# Publish

Run this before presenting any push, release, pull request, or other publication as ready, including when no new commit is needed. Commit approvals stay individual. For routine branch pushes, H approves one fixed ordered set of reviewed publication bindings; the agent then executes and verifies each binding separately. Grouped approval preserves separate commits and can leave partial completion if a later operation fails. Approval is contemporaneous and conversational; receipts record scope, never approval or blanket authority. The existing `publish-bind`, `publish-apply` and `publish-verify` scripts remain the per-binding procedure.

## Prepare and review

1. Run `~/.agents/skills/publish/scripts/publish-bind [<ref>]`, default `HEAD`, or add `--remote <remote> --branch <branch>` for H's named destination. Each binding names one resolved push endpoint, branch, immutable reviewed commit, tracking baseline (assumed without a fetch), and relevant configuration. Multiple separately approved commits on that branch can be published through one binding of their reviewed tip. A non-descendant is a destructive request for H's separate ruling. Multiple destinations in one binding, embedded endpoint credentials, unsupported helpers/options, and absent first-publication baselines refuse. Never bypass these or display credential-bearing values. First publication or audience expansion needs explicit complete-history review and an appropriate separately reviewed procedure, not an invented baseline.
2. Review every new commit and its metadata, including transient content removed before the tip. The script scans explicit per-parent merge patches, complete newly reachable objects and tree paths, and the flat diff. Actual sensitive/identity findings block readiness. A partial scan binds exact unscanned object IDs, sizes, reasons and historical tree/path locations: show metadata only and require H's inspection of those exact objects before approval. Never claim a complete scan from a partial result. Review the effective pre-push hook and intended behavior, including its target/content fingerprint; normal hooks remain enabled. A ready receipt means recorded scope, not completed human review. The audience is H's declared audience, else world-readable.
3. Run the repository's gates on the reviewed contents, using only the commit skill's conservative same-workstream evidence reuse rules. `commit-apply` provenance never substitutes for gates. Keep exact final-pair verification for coordinated twin repositories; a green check against an earlier peer does not validate the pair being published. Account for automatic CI/deployment effects and any release/PR metadata or assets. Approval also covers necessary failed-CI reruns for the exact published commits under CI reruns below; other remote mutations need their own authority. A push-set approval covers only its listed bindings and reviewed effects.
4. Establish the exact ordered set before presentation. Do not ask approval for an empty set. Require unique full IDs and one binding per destination/branch; resolve overlapping targets and their intended reviewed tip before approval rather than silently dropping a member or preparing conflicting leases. Record every full binding ID with its repository, endpoint/branch, base/reviewed commits and record-root context in the private workstream checkpoint, linked to its immutable receipt and gate/review evidence. Capture verbose helper output in owned private execution scratch when useful, and inspect it before summarizing. Retain the generated push argv and exact apply invocation for technical inspection; packet and executor share the same generator. Include no known blocked target in a ready set. Destructive or hard-to-reverse targets retain separate exact-target approval. Use individual mode when H requests it or a materially different consequence needs its own decision.

## Decision brief and approval

Present **one consolidated push summary followed by one approval selector for the listed set**. Do not print every technical packet and then ask again per repository. In individual mode, present one target's compact card and its selector immediately, without an upfront packet dump. Never combine or squash commits to fit either presentation.

The visible summary names each repository and short binding reference in execution order, its resolved destination/branch and audience, the reviewed commit count/subjects or concise change summary, operational effects such as CI/production deployment, and gate/scan/review results. Keep failed/skipped checks, unresolved privacy concerns, required manual inspection and other material exceptions visible. State retained-artifact obligations concisely. A normal push summary need not repeat full commit messages, parent/tree/base hashes, raw argv or receipt paths.

Full IDs, base/reviewed hashes, hook fingerprints, argv, exact execution context and detailed evidence stay in the technical record and are available on request. Short references are presentation aliases only: each must resolve unambiguously to the full immutable ID recorded before approval, never to a mutable latest record. Lengthen ambiguous references. Requesting details or choosing individual review causes no publication.

Use `Publish and resume` first and `Publish and pause` second, with the selector explicitly naming the fixed set and its target count/references. An optional `Review individually` choice switches mode without executing anything. Only a selected Publish option authorizes the listed set, one attempt per binding in that order. Free text is a question, revision or rejection, never approval. Changing membership, order, IDs, destination, reviewed content, audience or effects requires a revised summary and fresh approval; rebind affected scopes as needed. Do not silently substitute a new binding or add another repository after approval.

Clipboard copying remains optional and explicitly H-triggered. If requested, identify the exact selected binding and call `~/.agents/skills/publish/scripts/publish-clip --copy` once with its reviewed apply invocation, providing the repository/record-root context. Return to the selector without execution or verification. Copying is neither approval nor proof, and preparation/re-display never copies automatically.

## Execute and verify

1. Before the first attempt, re-read the fixed full-ID set and obtain any necessary native execution authority for its exact helpers and contexts. Run `publish-bind --check ID` for each pending binding from its recorded repository/root; stop if any preflight refuses. A native denial is a blocker, not permission to use a nested client, wrapper or weaker profile. Set approval never overrides native permissions.
2. Process the approved set in order with separate tool invocations. Run `~/.agents/skills/publish/scripts/publish-apply ID` from the matching repository with the same `EYRAGENTS_RECORD_ROOT`, accepting only the full ID and no forwarded options. The helper holds the common-directory lock across drift recheck and direct-argv execution. It preserves the configured remote name, reviewed SHA, one-branch refspec, exact-base lease, normal `--verify` hooks and tag/submodule/redirect suppression. It durably writes `executing` before its one client-noninteractive attempt, with a 300-second push timeout. No composed multi-repository push or batch executor is needed.
3. Run `~/.agents/skills/publish/scripts/publish-verify ID` immediately for that binding, including after an unsuccessful attempt where its context permits observation. It rechecks configuration, observes the bound push endpoint through read-only `ls-remote`, reports tracking separately, and runs trusted-worktree `make verify-published REV=<id>` or `npm run verify-published -- <id>` where defined. Account for those targets; the whole verifier is not intrinsically endpoint-only or read-only. Query hosted CI through read-only `gh`; pending/failed/unknown remain distinct, and twins need the exact final committed pair. Handle necessary failed-job retries through CI reruns below, without asking for the same commit/publication approval again.
4. Continue to the next listed binding only after successful execution and bound verification, with no known blocking CI/deployment failure. Stop the set on drift, failure, timeout, interruption, native refusal or uncertain state. Report completed, attempted and unattempted members separately. Even if observation shows a failed attempt landed, do not automatically resume the remainder. Continuing after a stop, pause or handoff needs a fresh summary and approval for the unattempted remainder; never replay attempted IDs. Pending CI alone is not a failure, but remains open verification work.

Only `ready` records execute. Success, failure, timeout, cancellation or launch failure consumes that binding's execution opportunity. Git success is not endpoint verification; failures after launch, including status-persistence failure, may have published. Never reset to ready, replay an ID or silently rebind to retry. A lost-result `executing` marker remains protected; handled attempts record `attempted` with execution and process-group cleanup evidence. Verification may promote an attempted record to verified while retaining even a failed execution result. Drift preserves attempted evidence. Observing an executing record cannot resolve its execution/cleanup or make it closeable. Remote equality is point-in-time evidence, not proof who pushed, and mismatch does not establish that the attempt never landed. Never mutate tracking to make checks pass.

HTTPS uses the configured credential helper, normally host-local `gh` for GitHub; SSH preserves the caller's configuration and inherited `SSH_AUTH_SOCK`. H manages login/storage/recovery locally, outside publication execution. Authentication readiness is distinct from approval. Independent providers may show recovery UI despite client noninteractive flags; process-group cleanup does not control provider-owned dialogs. Do not inspect credential stores, alter global authentication or weaken TLS/host trust/transport selection. Raw pushes remain denied.

Report one consolidated result for the set, including per-repository commits/destinations, endpoint verification, CI/deployment results and remaining work. `Publish and resume` continues authorized work and pending verification; `Publish and pause` completes the approved set and available verification, reports pending CI and stops for discussion. At overall completion, follow the commit skill's [Receipt Close-Out](../commit/SKILL.md#receipt-close-out), then remove unneeded scratch/checkpoint/review artifacts. Retain records needed by CI, recovery or a concrete paused handoff. H's accepted-unverified disposition can close eligible attempted records without a success claim; it never makes active/ambiguous state eligible.

## CI reruns

H's approval of the commits and their publication covers necessary retries of failed CI for those exact published repositories/commits, within the originally reviewed workflow effects. Do not add a second approval selector for that follow-up. This authority comes from H's conversational approval, not merely a receipt, a green local test, or the ability to run `gh`.

1. Establish the approved repository and full published SHA from the active workstream, re-read its publication evidence, and inspect the exact run with `gh run view RUN_ID --repo OWNER/REPO --json databaseId,headSha,headBranch,event,status,conclusion,attempt,jobs,url`. Substitute literal reviewed values. Require the run to belong to that destination, its `headSha` to equal the published SHA, and its `headBranch`/`event` to match the reviewed CI trigger. Inspect the selected job's `databaseId` and failed conclusion within that run. Pending, successful, cancelled, approval-waiting, unrelated or unidentifiable runs are not an automatic retry target.
2. Read the failed job's logs and diagnose a retryable cause, such as a runner/network failure or a twin job that fetched the old peer before its approved companion push completed. Confirm the prerequisite is now satisfied. Genuine source failures require their own reviewed fix and new commit/publication approval. Check the workflow and dependencies a rerun would execute: replaying a deployment or other consequential side effect needs separate approval unless that repeated effect was already included in the publication review.
3. State the diagnosed cause and exact target briefly, record the run ID, attempt, job ID, reason and planned command in the active checkpoint, then use `gh run rerun RUN_ID --repo OWNER/REPO --job JOB_ID`. Prefer the smallest failed-job scope. Use `--failed` only when all failed jobs and their dependencies are within the same reviewed retry scope. Do not rerun the entire workflow or enable debug logging merely for convenience; never use a new workflow dispatch, cancellation or an approval bypass as a substitute.
4. Make one retry for the diagnosed cause, then observe the new attempt with `gh run view`/`gh run watch` and inspect its result. If the rerun command fails or its outcome is uncertain, inspect the run before any further mutation; do not blindly repeat it. An unchanged repeat failure stops automatic retries and returns to diagnosis. A distinct newly established transient cause may justify another bounded retry, not an unattended retry loop.
5. Record the observed new attempt/result. For twins, inspect the actual pair in the successful job's log and require the final published commits. A rerun does not replay or reauthorize `publish-apply`, repair a binding, or resume an unattempted push-set remainder after a stop. Keep required evidence through CI verification, then use normal receipt close-out.

These scope checks are enforced by the primary's workflow, not by the native command matcher. OpenCode permits the `gh run rerun` command family; Claude Code's classifier recognizes this approved-publication exception, and Hermes follows shared guidance with native review. Codex's command-network restriction still prevents execution in its ordinary profile. A native denial requires authorized configuration/activation or handoff, never a wrapper, alternate API or nested client to evade it. After changing OpenCode permissions, quit and restart/resume it before retrying a denied command.

## Codex handoff

Codex retains its command-network and protected-file restrictions. Its denied-read policy prevents native unsandboxed execution even after approval, so do not invoke `publish-apply` there or add an ineffective reviewer exception. Prepare review and record pending work in the existing checkpoint. H opens a separate Claude Code, OpenCode or Hermes primary in the same trusted repository. It re-reads the checkpoint, checks Git state and each binding/record-root context, repeats necessary review or rebinds on drift, and obtains H's fresh approval of the exact pending set. Neither checkpoint nor prior session transfers approval. No nested client, broker, retained grant or policy override is authorized. The receiving context also verifies, accounting for trusted-worktree targets. Opaque/custom SSH expressions can leave execution/observation unavailable; report the limitation rather than looping through rebinds or substituting an endpoint. Restart affected clients after harness deployment to load changed skills and commands.
