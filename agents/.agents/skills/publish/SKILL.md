# Publish

Run this before presenting any push, release, pull request, or other publication as ready, including when no new commit is needed. H approves the exact repository/binding packet; the agent executes one `publish-apply ID` attempt and verifies separately. Approval is contemporaneous and conversational, as with `commit-apply`; a receipt records scope, never approval or blanket push authority. The `publish-bind`, `publish-apply` and `publish-verify` scripts carry the procedure.

1. Run `~/.agents/skills/publish/scripts/publish-bind [<ref>]`, default `HEAD`, or add `--remote <remote> --branch <branch>` for H's named destination. It binds a single resolved push endpoint, branch, reviewed commit, tracking baseline (assumed without a fetch), and relevant configuration to an immutable `binding-id`. A non-descendant is a destructive request for H's separate ruling. Multiple destinations, embedded endpoint credentials, unsupported helpers/options, and absent first-publication baselines refuse; never bypass these or display credential-bearing values. First publication or audience expansion needs explicit complete-history review and an appropriate separately reviewed procedure, not an invented baseline.
2. Review every new commit and its metadata, including transient content removed before the tip. The script scans explicit per-parent merge patches, complete newly reachable objects and tree paths, and the flat diff. Actual sensitive/identity findings block readiness. A partial scan binds exact unscanned object IDs, sizes, reasons and historical tree/path locations; show metadata only and require H's inspection before publication, never claim a complete scan. Review the bound effective pre-push hook and intended behavior, including symlink target/content digest; normal hooks remain enabled. A ready receipt means recorded scope, not completed human review. The audience is H's declared audience, else world-readable.
3. Run the repository's gates on the reviewed contents, using only the commit skill's conservative same-workstream evidence reuse rules. `commit-apply` provenance never substitutes for gates. Keep exact final-pair verification for coordinated twin repositories: a green check against an arbitrary earlier peer does not validate the pair being published.
4. Account for anything else the operation would publish: release or pull request metadata, bodies, and assets.
5. Put the complete compact packet in normal visible chat: repository/`binding-id`, bound destination/base/reviewed IDs, commits, gates/scan/privacy/hooks, required inspection, disposition, printed push argv, exact apply invocation and its repository/record-root context. The displayed argv and executor share one generator: configured remote name, immutable reviewed SHA, one-branch refspec, exact-base lease, normal `--verify` hooks, and tag/submodule/redirect suppression. Rebind/review changed configuration, scope or audience. Present all per-repository packets together in dependency order, but approve and execute one exact target at a time, with separate invocations rather than a composed shell command. Use a short selector naming the exact repository/ID, `Publish and resume` first and `Publish and pause` second. Only a selected publish option authorizes that binding; free text is a revision, rejection or question, never approval. Revisions need fresh binding/review. Optional `Copy publish command` or an explicit copy request triggers one `~/.agents/skills/publish/scripts/publish-clip --copy` call with the displayed apply invocation, then returns to the selector without execution or verification. Copying is neither approval nor proof. Never copy on preparation/re-display or claim the clipboard still contains an earlier copy.
6. Before invoking, obtain any necessary native execution authority for that exact helper, ID and bound context. A blocked route is a blocker, not a reason to start inside a network-disabled sandbox and automatically retry outside it. Run `~/.agents/skills/publish/scripts/publish-apply ID` from the bound repository with the same record root, accepting no extra arguments or forwarded options. It holds the common-directory lock across the drift recheck and direct argv push, durably marks `executing` before launch, and makes one client-noninteractive attempt with a 300-second push timeout. HTTPS uses the configured credential helper, normally host-local `gh` for GitHub; SSH retains the caller's configuration and inherited `SSH_AUTH_SOCK`. H manages login/storage/recovery locally, outside publication execution. Authentication readiness is distinct from the selected publication approval. Independent providers can show recovery UI despite client noninteractive flags; the executor's process-group cleanup does not control provider-owned dialogs. Do not inspect credential stores, alter global authentication or weaken TLS/host trust/transport selection. Raw pushes remain denied. Only `ready` can execute; success, failure, timeout, cancellation or launch failure consumes the execution opportunity. Git success is execution evidence, not endpoint verification. Errors after launch may have published, including status-persistence failure. Never reset to ready, replay the ID, or silently rebind to retry. A lost-result `executing` marker stays protected for H; handled attempts record `attempted` with their outcome and process-group cleanup evidence.
7. Run `~/.agents/skills/publish/scripts/publish-verify ID` for each exact binding with its record root, including independent observation after an unsuccessful attempt where the context permits it. It checks bound configuration again, observes the bound push endpoint through read-only `ls-remote`, reports local tracking separately, and runs trusted-worktree `make verify-published REV=<id>` or `npm run verify-published -- <id>` where defined. The whole verifier is therefore not intrinsically endpoint-only or read-only. Query relevant hosted CI separately through read-only `gh` checks, reporting pending/failed/unknown honestly; for twin changes verify the exact final committed pair and identify any hosted pair run still needed. Remote equality is point-in-time evidence, not proof who pushed; stale tracking or later mismatch does not establish that the attempt never landed. Offline/error results are unknown. Verification can promote `attempted` to `verified` while retaining execution evidence; drift preserves attempted evidence. Observation of `executing` reports equality if available but cannot resolve its execution/cleanup or close it. Stop on unexpected state, arrange recovery with H, and never mutate tracking to make checks pass. After verification, `resume` continues remaining authorized work; `pause` stops for discussion. At overall completion, follow the commit skill's [Receipt Close-Out](../commit/SKILL.md#receipt-close-out), then remove unneeded scratch/checkpoint/review artifacts. Keep records needed by CI, recovery or a concrete paused handoff. H's accepted unverified disposition can close eligible attempted records without a success claim; it does not make active/ambiguous state eligible. Report every repository and retained item together.

Codex retains its command-network and protected-file restrictions. The configured denied-read policy prevents native unsandboxed execution even after approval, so do not invoke `publish-apply` there or add a reviewer exception that cannot supply the required authority. Prepare the review and record its pending work in the existing workstream checkpoint. H opens a separate Claude Code, OpenCode or Hermes primary in the same trusted repository. That primary re-reads the checkpoint, checks Git state and the exact binding/record-root context, repeats necessary review or rebinds on drift, and obtains H's fresh exact-binding approval before execution. Neither a checkpoint nor a prior session transfers approval. Do not launch a nested client, broker, retained grant or policy override to route around the Codex boundary. The receiving network-capable context also performs verification, accounting for trusted-worktree targets. Opaque/custom SSH expressions can leave execution/observation unavailable there too. Arrange verification deliberately; do not loop through ineffective rebinds or substitute a different endpoint. Restart affected clients after harness deployment; source changes do not replace the running session's loaded policies or skills.
